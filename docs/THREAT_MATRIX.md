# Protocol Security & STRIDE Threat Model Assessment

This document provides a rigorous, auditor-grade security assessment, STRIDE threat model, memory safety evaluation, and reverse-engineering complexity analysis for binary protocols generated by `gen_protocol.py`.

> [!IMPORTANT]
> **Security Disclaimer**: Protocols generated by `gen_protocol.py` are unencrypted, unauthenticated binary framing schemas. They provide framing integrity (CRC-32) and memory safety (bounds checking), but do **NOT** provide cryptographic confidentiality, message authenticity, or anti-tampering guarantees without a transport security layer (such as TLS 1.3 or Noise Protocol).

---

## 🎯 1. STRIDE Threat Model & Countermeasure Matrix

| STRIDE Threat Category | Real Threat Description | Unmitigated Risk Level | Mitigation & Implementation Reality |
|---|---|---|---|
| **Spoofing (Header / Magic)** | Attacker injects frames with spoofed `magic` constant or `session_id`. | **HIGH** | **Magic Check**: `hdr_validate()` checks `magic == MY_PROTO_MAGIC` (returns `MY_PROTO_HDR_ERR_MAGIC` (-1)). *Reality:* `magic` is sent in plaintext on the wire; anyone who captures a packet can read and spoof it. Cryptographic derivation (SHA-256 over `name:seed`) only prevents cross-protocol magic collisions, not active wire spoofing. |
| **Tampering (Active Malicious Modification)** | Attacker alters frame header or payload bytes in transit. | **HIGH** | **CRC-32 Checksum (`crc32`)**: Checked via `hdr_validate()` (returns `MY_PROTO_HDR_ERR_CRC` (-5)). *Reality:* CRC-32 is an **unkeyed error-detection code** designed for passive bit-rot/noise detection. An active attacker can modify bytes and recompute a valid CRC-32 in microseconds. **Requires HMAC or TLS for active anti-tampering protection.** |
| **Repudiation / Replay Attacks** | Attacker captures and re-sends valid historical frames. | **MEDIUM** | **Anti-Replay Window (`replay_check`)**: Each generated protocol ships an opt-in IPsec-style sliding bitmap window (`<proto>_replay_check()`, width `REPLAY_WINDOW=64`) that the receiver invokes per session after `hdr_validate()`. It is wraparound-safe, tolerates out-of-order delivery within the window, and rejects exact replays, already-seen, and stale frames. *Reality:* **Opt-in** — `hdr_validate()` is stateless, so the application must keep one zero-initialised `<proto>_replay_state_t` per `session_id` and call `replay_check()` on every received frame. It blocks re-sent captured frames only; it is not authentication and does not stop an active forger from emitting *new* frames. |
| **Information Disclosure** | Passive eavesdropper reads frame headers and payload fields. | **HIGH** | **No Default Encryption**: Payload fields and headers are transmitted in plaintext wire format. Encryption must be provided at the transport layer (TLS/DTLS/Noise). |
| **Denial of Service (Buffer Overflow)** | Attacker sends oversized `payload_len` to trigger heap/stack overflow. | **LOW** | **Strict Bounds Checking**: `hdr_validate()` enforces two distinct bounds checks:<br>1. `hdr->payload_len > MAX_PAYLOAD` returns `MY_PROTO_HDR_ERR_PAYLOAD_TOO_BIG` (-3).<br>2. `hdr->payload_len != (uint16_t)payload_len` returns `MY_PROTO_HDR_ERR_LEN_MISMATCH` (-4). |
| **Elevation of Privilege (Opcode Injection)** | Attacker sends malformed or unexpected opcode values. | **MEDIUM** | **Enum Range Validation**: `hdr_validate()` checks opcode against switch-case table (returns `MY_PROTO_HDR_ERR_OPCODE` (-6) if unknown). *Reality:* Validates schema membership only; does not enforce sender authorization or payload semantic validity. |

## 🔬 2. Reverse-Engineering & Obfuscation Analysis

Protocols generated by `gen_protocol.py` do not use inline type tags (like JSON or Protobuf fields). Instead, payloads are raw packed C structs (`PROTO_PACKED`).

| Dimension | Reverse Engineering Complexity Analysis |
|---|---|
| **Format Non-Standardness** | **Moderate**: Lacking standard TLV (Type-Length-Value) or JSON tags, reverse engineers analyzing raw pcap dumps or stripped binaries must trace assembly instructions (`msg_decode`) in Ghidra/IDA Pro to recover struct field offsets. |
| **Signature Analysis** | **Moderate**: SHA-256 derived magic constants prevent static signature detectors (`binwalk`) from matching known protocol signatures (like PNG or Protobuf). However, the magic constant is easily read from the first 4 bytes of any captured packet. |
| **Bitfield Storage** | **Low to Moderate**: Bitfields ($1..4$ bits) are packed into integer storage cells and accessed via `GET_*` / `SET_*` bitmask macros, generating standard bitwise `AND`/`SHR` instruction patterns in compiled binaries. |
| **MultiChain Tunneling** | **Moderate**: In `--multichain N` suites, cross-chain bridge messages (`*_MSG_BRIDGE_TO_*`) encapsulate target chain payloads inside a 128-byte array (`tunnel_payload`), requiring multi-hop frame unpacking. |

## 🛡️ 3. Memory Safety & API Error Contract

The generated C implementation provides exact memory safety and explicit error return codes:

### Header Validation Error Codes (`my_proto_hdr_err_t`)

```c
typedef enum {
    MY_PROTO_HDR_OK                  =  0,  /* Frame header and payload are valid */
    MY_PROTO_HDR_ERR_MAGIC           = -1,  /* Magic constant mismatch (hdr->magic != MY_PROTO_MAGIC) */
    MY_PROTO_HDR_ERR_VERSION         = -2,  /* Version mismatch (hdr->version != MY_PROTO_VERSION) */
    MY_PROTO_HDR_ERR_PAYLOAD_TOO_BIG = -3,  /* Payload length exceeds MY_PROTO_MAX_PAYLOAD limit */
    MY_PROTO_HDR_ERR_LEN_MISMATCH    = -4,  /* Header payload_len != actual buffer length */
    MY_PROTO_HDR_ERR_CRC             = -5,  /* CRC-32 checksum mismatch */
    MY_PROTO_HDR_ERR_OPCODE          = -6   /* Opcode unknown or unsupported by protocol schema */
} my_proto_hdr_err_t;
```

### Memory Safety Guarantees
1. **No Undefined Behavior in Float Conversions**: `float` and `double` wire swapping uses `memcpy` bit re-interpretation via `proto_f32_to_u32_` and `proto_u64_to_f64_` to strictly comply with ISO C strict aliasing rules.
2. **Struct Padding Control**: All wire structures use `#pragma pack(push, 1)` or `__attribute__((packed))` (`PROTO_PACKED`), preventing compiler padding vulnerabilities.

## 🔒 4. Production Security Hardening Checklist

To deploy generated protocols securely in untrusted network environments:

- [ ] **Transport Security**: Wrap TCP/UDP sockets in **TLS 1.3**, **DTLS 1.3**, or the **Noise Protocol Framework** (e.g. `Noise_IK_25519_ChaChaPoly_BLAKE2b`).
- [x] **Sequence Window Tracking**: Generated per protocol as `<proto>_replay_check()` (IPsec-style sliding bitmap, width 64, wraparound-safe). Opt-in: keep one zero-initialised `<proto>_replay_state_t` per `session_id` and call it after every successful `hdr_validate()`.
- [ ] **Message Authentication (MAC)**: If running over raw UDP without TLS, append an **HMAC-SHA256** tag over the frame and verify it using a shared secret before calling `hdr_validate()`. (CRC-32 remains forgeable; `replay_check` does not authenticate.)
