# Protocol Security & STRIDE Threat Model Assessment

This document provides a rigorous, auditor-grade security assessment, STRIDE threat model, memory safety evaluation, and reverse-engineering complexity analysis for binary protocols generated by `gen_protocol.py`.

---

## 🎯 1. STRIDE Threat Model & Countermeasure Matrix

| STRIDE Threat Category | Real Threat Description | Unmitigated Risk Level | Mitigation & Implementation Reality |
|---|---|---|---|
| **Spoofing (Header / Magic)** | Attacker injects frames with spoofed `magic` constant or `session_id`. | **LOW (with `--auth`)** / HIGH (plain) | **HMAC-SHA256 Authentication (`--auth hmac-sha256`)**: When enabled, `<proto>_frame_mac()` and `<proto>_mac_verify()` enforce cryptographic origin verification with constant-time comparison (`_const_time_memcmp`) over `header(crc=0) \|\| payload`. Frames without a valid symmetric key MAC are rejected with `HDR_ERR_AUTH_FAIL` (-8). |
| **Tampering (Active Modification)** | Attacker alters frame header or payload bytes in transit. | **LOW (with `--auth`)** / HIGH (plain) | **Dual Integrity & Auth Checking**: 1. **CRC-32**: Checked via `hdr_validate()` for channel bit-rot detection (`HDR_ERR_CRC`, -5). 2. **HMAC-SHA256**: Appends a 32-byte cryptographic trailer tag verified before payload dispatch, preventing active adversaries from recomputing valid checksums. |
| **Repudiation / Replay Attacks** | Attacker captures and re-sends valid historical frames. | **LOW** | **Sliding Bitmap Anti-Replay (`<proto>_replay_check`)**: Built-in IPsec-style sliding bitmap window (`REPLAY_WINDOW=64`) per session. Wraparound-safe signed sequence deltas tolerate out-of-order delivery while rejecting seen, duplicate, and stale frames. |
| **Information Disclosure** | Passive eavesdropper reads frame headers and payload fields. | **HIGH (plain)** | **Transport Layer Encryption**: Payloads and headers are transmitted in packed binary wire format. Full end-to-end confidentiality requires a transport layer such as TLS 1.3, DTLS 1.3, or the Noise Protocol Framework. |
| **Denial of Service (Buffer Overflow & Truncation)** | Attacker sends oversized or truncated `payload_len` to trigger heap/stack overflow. | **LOW** | **Multi-Tier Bounds & Schema Validation**:<br>1. `hdr->payload_len > MAX_PAYLOAD` returns `HDR_ERR_PAYLOAD_TOO_BIG` (-3).<br>2. `hdr->payload_len != (uint16_t)payload_len` returns `HDR_ERR_LEN_MISMATCH` (-4).<br>3. `hdr->payload_len != expected_payload_len(opcode)` returns `HDR_ERR_LEN_SCHEMA` (-7). |
| **Elevation of Privilege (Opcode & IDL Injection)** | Attacker sends malformed opcodes or injects malicious C statements via IDL YAML. | **LOW** | **Strict Whitelisting & Identifier Sanitization**:<br>1. Opcodes strictly validated against enum switch-case (`HDR_ERR_OPCODE`, -6).<br>2. IDL compiler validates all identifiers with `^[A-Za-z_][A-Za-z0-9_]{0,63}$`, blocks C reserved keywords, and strips comment break-out sequences (`/*`, `*/`). |

## 🛡️ 2. Memory Safety & Error Return Codes

### Header Validation Error Codes (`<proto>_hdr_err_t`)

```c
typedef enum {
    MY_PROTO_HDR_OK                  =  0,  /* Frame header and payload are valid */
    MY_PROTO_HDR_ERR_MAGIC           = -1,  /* Magic constant mismatch */
    MY_PROTO_HDR_ERR_VERSION         = -2,  /* Version mismatch */
    MY_PROTO_HDR_ERR_PAYLOAD_TOO_BIG = -3,  /* Payload length exceeds MAX_PAYLOAD limit */
    MY_PROTO_HDR_ERR_LEN_MISMATCH    = -4,  /* Header payload_len != buffer length argument */
    MY_PROTO_HDR_ERR_CRC             = -5,  /* CRC-32 checksum mismatch */
    MY_PROTO_HDR_ERR_OPCODE          = -6,  /* Opcode unknown or unsupported by protocol schema */
    MY_PROTO_HDR_ERR_LEN_SCHEMA      = -7,  /* Payload length does not match message schema */
    MY_PROTO_HDR_ERR_AUTH_FAIL       = -8   /* HMAC-SHA256 authentication verification failed */
} my_proto_hdr_err_t;
```

### Memory Safety & Fuzzing Guarantees
1. **Schema Length Enforcement (`<proto>_expected_payload_len`)**: Every message struct's exact wire byte size is generated into a fast opcode dispatch function, preventing payload truncation attacks.
2. **Strict Aliasing Compliance**: `float` and `double` conversions strictly use `memcpy` bit re-interpretation routines (`proto_f32_to_u32_` / `proto_u64_to_f64_`).
3. **Struct Padding Control**: All wire structures use `#pragma pack(push, 1)` or `__attribute__((packed))` (`PROTO_PACKED`).
4. **Continuous Fuzzing (`--fuzz`)**: Generates a standalone libFuzzer harness (`LLVMFuzzerTestOneInput`) and valid binary seed corpus, testable with Clang AddressSanitizer (ASan) and UndefinedBehaviorSanitizer (UBSan).

## 🔒 3. Zero-Dependency Cryptographic Authentication (`--auth hmac-sha256`)

When invoked with `--auth hmac-sha256` (or `auth: hmac-sha256` in YAML IDL):
- The emitter compiles a standalone, zero-dependency embedded implementation of **FIPS 180-4 SHA-256** and **RFC 2104 HMAC**.
- Provides constant-time memory comparison (`<proto>_const_time_memcmp`) to eliminate timing side-channel attacks.
- Frame MAC is computed over `header(crc32=0) || payload` in wire byte order.

## 🧪 4. Fuzzing Infrastructure (`--fuzz`)

```bash
# 1. Generate protocol with fuzzing harness and seed corpus
python3 gen_protocol.py -p rpc --fuzz --auth hmac-sha256 -o out/fuzz_target/

# 2. Compile harness with libFuzzer + ASan + UBSan
clang -fsanitize=fuzzer,address,undefined -O2 -o fuzz_harness \
      out/fuzz_target/valkyrie_flow_fuzz.c out/fuzz_target/valkyrie_flow.c

# 3. Run continuous fuzzing against the seed corpus
./fuzz_harness out/fuzz_target/corpus/ -max_len=2048 -timeout=10
```
